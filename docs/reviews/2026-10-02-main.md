## Summary

This is the online booking checkout feature (spec 0015): a public, unauthenticated write path (hold → pay by QR → confirm) gated by Turnstile, a 60-second minted `online_booking` Postgres role, and a set of `SECURITY DEFINER` functions that own every real rule (price, hours, overlaps, the 15-minute rate limit, idempotency on `submission_id`). The implementation is unusually careful: price and code are generated entirely in Postgres, every business refusal is a typed `jsonb` answer parsed through Zod rather than trusted, the storage policies for the payment-proof bucket are backstopped by a write-guard trigger that closes a real TOCTOU the team found by testing against the linked project (a signed upload URL outliving `submitted_at`), and the retention constants that drive `/privacy`'s copy are the same constants a database test seeds into the purge functions. Database test coverage (`supabase/tests/online_booking*.test.ts`, ~900 lines) and action-level unit tests (`lib/booking/actions.test.ts`) both look thorough and exercise the refusal branches, idempotency, and analytics side effects explicitly called out in the spec. I found no blockers or majors. The one real issue is a minor, unused field that leaks more than the spec's own invariant allows for.

## Minor

### 🟡 The hold response sends an internal storage path the browser never uses, `lib/booking/types.ts:23` / `lib/booking/actions.ts:162`

**Problem**: `holdOnlineBooking` returns `upload: { path: held.proof_path, signedUrl }` to the browser (`HeldBooking.upload.path` in `lib/booking/types.ts:23`). Nothing in the client reads `upload.path` — `useProofUpload` in `components/landing/checkout-payment.tsx:208` is constructed from `held?.upload.signedUrl` only, and `uploadProof()` in `lib/booking/proof.ts` takes only a `signedUrl`. A repo-wide grep confirms `upload.path` has no reader anywhere in `components/landing` or `lib/booking`.
**Why it matters**: AC-20 states "No page, JSON response or broadcast that anyone other than the player can reach carries an email, reference digits, proof path, code, or client hash", with the parenthetical exception naming only "their own code and digits" for the player's own results — proof path is not included in that exception. Sending it anyway is a literal deviation from a stated invariant, and it has no justification since it is dead data: it discloses the booking's internal numeric id (`proof_path` is `<booking id>/<submission id>`) for no functional gain.
**Suggested fix**: Drop `path` from the object `holdOnlineBooking` returns (keep `held.proof_path` as a local variable used only to build the signed URL), and remove it from `HeldBooking.upload`.

## Nits

- ⚪ `lib/booking/actions.ts:52-59`, `onlineBookingSupabase()` calls `mintOnlineBookingToken(clientHash)` (an `async` function) without `await`, relying on `accessToken: () => token` returning the un-awaited promise to supabase-js. It works, but an explicit `await` plus `accessToken: async () => token` would make the fresh-mint-per-call contract easier to verify at a glance.

## Strengths

- The `payment_proof_lock` migration (`supabase/migrations/20260929224308_payment_proof_lock.sql`) adds a `before insert or update` trigger on `storage.objects` that re-checks `is_open_proof_path` at write time, closing a real gap the team found by testing live: a signed upload URL survives 2 hours past `submitted_at`, so the storage *policies* alone (checked only when the URL is signed) aren't enough to stop a replace after confirm. This is exactly the kind of defense-in-depth a review would otherwise have to ask for.
- The retention story is unusually tight: `lib/legal/constants.ts` numbers are literally quoted into `/privacy`, and `supabase/tests/online_booking_retention.test.ts` seeds the same constants into its boundary assertions against `purge_online_booking_details()` and `payment_proofs_due()`, so the page and the SQL cannot silently drift apart.
- `lib/booking/actions.test.ts` and the database tests both exercise the full refusal matrix (slot_taken, out_of_range, rate_limited, bot_check, proof_missing, not_found, invalid) and pin which ones fire an analytics event vs. a `console.warn`, matching AC-24 precisely.
