## Summary

Spec 0016 (staff check of online bookings) is implemented thoroughly: the four decision functions are `security definer`, check `private.is_owner()` first, guard on `version`, and write exactly one `booking_event`; the `guard_online_reservation()` trigger correctly enforces that only a decision function can cancel/reprice/repay a row of a `held`/`pending_check`/`confirmed` booking, and copies contact edits without bumping the booking's version. The client side (chip, list, details sheet, turn-down/cancel/refund steps, screenshot viewer, toast) is well organized and the database test suite (`supabase/tests/online_checks.test.ts`) covers every refusal path in AC-15. The one real blocker is unrelated to the feature: `lib/venue.ts` was edited to remove the payment placeholders, which flips `checkoutEnabled()` live wherever the Turnstile env vars are set — a production-risk change bundled into this diff with no connection to spec 0016. There is also a real, if narrow, gap in the row guard's scope for already-decided bookings.

## Major

### 🟠 The row guard only protects a booking while it is open, not after it is decided, `supabase/migrations/20261002163852_online_checks_turn_down.sql:41-54`

**Problem**: `guard_online_reservation()` only raises when `v_status in ('held', 'pending_check', 'confirmed')`. Once a booking is `rejected`, `cancelled` or `expired`, a direct `update reservation set payment_status = ..., amount = ...` (or a crafted call into `updateReservation`, which has no app-level check tying `paymentStatus`/`amount` to `bookingId === null`, relying entirely on the trigger) passes through untouched. The reservation update RLS policy (`court_schedule.sql:397-405`) only requires `ends_at > now() or is_owner()`, so an owner-level staff member (the only one who could reach an un-ended row anyway, given the "ended row" rule) can silently change `payment_status`/`amount` on an already-decided online booking's row, with no `booking_event`, no `version` bump on `booking`, and no trace beyond the row's own audit log.
**Why it matters**: Invariant 7 in the spec states, without qualification, that "an online row's amount and payment_status change only inside a decision function for its own booking." The implementation only holds that while the booking is still open. The UI never exposes these fields on an online row today, so this is not reachable through normal staff workflow, but it is reachable through any direct call to `updateReservation`, and it breaks the single source of truth the whole feature is built around (Postgres as the only writer of a decided booking's money fields).
**Suggested fix**: Either widen the guard's condition to also refuse `payment_status`/`amount` changes whenever the row has a `booking_id` (regardless of the booking's status, mirroring the unconditional `booking_id` check already in the same function), or narrow invariant 7's wording in the spec to match the "while open" scope the Decision section actually describes, and note the residual risk explicitly.

## Minor

### 🟡 Guard-refusal message is duplicated instead of shared, `lib/actions.ts:1422-1427` vs `lib/online-checks/constants.ts:94`

**Problem**: `lib/actions.ts`'s `describeDatabaseError` hardcodes `"This is an online booking. Use its own buttons in the sheet."` inline, even though the identical string already exists as `GUARD_MESSAGE` in `lib/online-checks/constants.ts`.
**Why it matters**: `lib/actions.ts` sits below `lib/online-checks/` in the dependency graph (the reverse import would be a layering violation), so this duplication is understandable, but it means the two strings can silently drift on a future wording change, and nothing would catch it except a human proofreading both files.
**Suggested fix**: Either move `GUARD_MESSAGE` (and `STALE_MESSAGE`-style constants that are really generic) to `lib/actions.ts` or a shared location, or add a one-line test asserting the two strings stay equal, the way `lib/schedule/constants.test.ts` already pins SQL check constraints against TS constants.

### 🟡 `getOnlineChecks()`'s `pending_check` read has no cap in the query itself, `lib/online-checks/queries.ts:126-141`

**Problem**: The `pending_check` branch reads up to 1000 rows (`.limit(1000)`) and sorts/slices to 50 in JavaScript, while the Decision section's stated rationale ("the unchecked ones are read whole so the sort by first slot is right, then capped at 50") only justifies reading more than 50, not an arbitrary 1000. This is a deliberate, documented tradeoff, not an oversight, but 1000 rows each carrying nested `reservation(...)` is a non-trivial read if a venue's queue ever grows unexpectedly (e.g. a bug upstream stops anyone from checking payments for weeks).
**Why it matters**: Low risk today given the stated venue size, but it is the one unbounded-ish query in an otherwise tightly capped feature, and a runaway queue would make every staff board's refetch (which happens on every `booking_changed`/`reservation_changed` event) progressively heavier.
**Suggested fix**: Nothing required now; worth revisiting if the cap of 1000 is ever hit in production (the venue's own dashboard would have bigger problems by then anyway).

## Strengths

- The guard trigger (`guard_online_reservation()`) and the four decision functions are a clean, well-commented implementation of "Postgres is the enforcement point": every refusal path (plain-staff direct RPC calls, direct row updates, `booking_id` reassignment) is exercised in `supabase/tests/online_checks.test.ts`, and the transaction-local `set_config` flag is explicitly cleared at the end of each function so a longer-lived transaction (a test, a future caller) can't accidentally inherit it.
- `standingRows()` and `timeTag()` both degrade gracefully when a `pending_check` booking has no active rows left (the exact legacy-data scenario called out for this review) — no crash, a sensible fallback display, and the sort places such an item last rather than throwing.
- The step-local `version` handling in `use-online-booking.ts` (a step keeps the version it opened on; Confirm always sends the version on screen) precisely matches AC-14's subtle requirement that a live read landing mid-step must not let a decision ride on a newer version than the manager saw.
